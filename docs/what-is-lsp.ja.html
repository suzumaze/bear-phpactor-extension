言語サーバーは、実際には何をしているのか

エディタの補完や「定義へ移動」の裏側で、実際にどんなバイト列が流れているのか。 この文書に載せた通信は、すべて手元のphpactorに実際に話しかけて記録した本物です。 作り話のサンプルは1つもありません。

記録日: 2026年8月24日 ／ 対象: phpactor（PHP用の言語サーバー） ／ 記録に使ったスクリプト: docs/capture/lsp-capture.php ／ 全ログ: docs/capture/lsp-capture.txt ／ 題材: docs/capture/lsp-demo/

01言語サーバーとは、エディタの外にいる「コードを読める人」

エディタ自身は、開いているファイルがPHPなのかRustなのかを本当は知りません。 知っているふりをするために、昔はエディタごとに言語ごとの実装を書いていました。 エディタが10個、言語が20個あれば、200通りの実装が要ります。

LSP（Language Server Protocol＝言語サーバープロトコル）は、そこに1枚の共通の話し方を挟みました。 言語の知識を持つ別プロセスを1つ立て、エディタはそのプロセスに決まった形式で質問する。 これで200が10＋20、つまり30で済みます。 Microsoftが2016年にVS Codeのために公開し、いまはVim・Neovim・Emacs・Helix・Zedなど、 ほぼすべてのエディタが対応しています。

だから「PHPの言語サーバーを1つ書く」と、その恩恵は特定のエディタに閉じません。 これがBEAR.Sundayの支援をphpactorの拡張として作る理由です。 PhpStormのプラグインはPhpStormだけのものですが、言語サーバーの拡張はどのエディタからも使えます。

02通信の実体は、ヘッダーが1行ついたJSON

エディタとサーバーは、標準入出力（多くの場合はパイプ）で繋がっています。 そこを流れるのは、HTTPに似たヘッダーと、JSONの本文を空行で区切ったものです。 これが実際に流れた最初の1通、生のバイト列そのままです。

読み方はこうです。 Content-Length: 177 は「このあと本文が177バイト続く」という宣言。 続く区切りは改行2つ（正確には\r\n\r\n）。そのあとがJSONです。

本文の形はJSON-RPC 2.0という既存の規約に従います。中身は4つだけです。

キー意味
jsonrpc常に "2.0"。この規約に従っているという印
id質問の通し番号。答えは同じ番号を付けて返るので、順番が前後しても対応が分かる
method何を聞いているか。initialize、textDocument/definition など
paramsその引数
「通知」にはidが無い

idを持つものはリクエストで、必ず答えが返ります。 idが無いものは通知で、答えは返りません。 「ファイルを開いた」「保存した」のような、返事の要らない報告に使います。 後で出てくるinitializedやtextDocument/didOpenがそれです。

03最初のやりとりは、できることの申告

接続すると、まずエディタがinitializeを送り、サーバーが自分にできることの一覧を返します。 これが実際に返ってきたものです（2,046バイトあるので、要点だけ抜いています）。

"definitionProvider": true が「定義へ移動に答えられます」という申告です。 ここがfalseや未定義なら、エディタはそもそも聞いてきません。 エディタのメニューが灰色になるかどうかは、この1行で決まります。

triggerCharactersも面白いところです。 ->の>や$を打った瞬間に補完を出してほしい、という要求で、 エディタはこの文字が入力されたときだけ自動で補完を聞きに行きます。

serverInfoの名前は、拡張が動いている証拠にはならない

"name":"bear/phpactor-extension"は、いま作っているパッケージの名前です。 一見「拡張が入った状態の記録だ」と読めますが、違います。 この名前はphpactorの実行ファイルが置かれているディレクトリのcomposer.jsonから 取られているだけで、拡張が読み込まれたかどうかとは無関係です。

実際に確かめました。この拡張は読み込まれるとvar/extension-loadedという印を書きます。 記録は13時25分と13時35分に取りましたが、印の更新時刻は11時32分のまま動いていません。 つまりこの記録は素のphpactorのものです。 理由は明確で、拡張は.phpactor.json経由でしか読み込まれず、 そのファイルは信頼登録したディレクトリでしか読まれないところ、 題材にした/tmp/lsp-demoを信頼登録していなかったためです。

この文書の目的にとっては、むしろ好都合でした。 ここに載っている往復は拡張抜きのphpactorが標準で答えている姿で、 BEAR.Sundayの拡張は、この同じ流れに1枚割り込むだけのものだからです。

04ファイルの中身は、ディスクではなくエディタから来る

次にエディタは「このファイルを開いた」と報告します。 注目してほしいのは、ファイルの本文を丸ごと送っていることです。

サーバーはパスを受け取っているのだから、自分でディスクを読めばよさそうに見えます。 そうしないのは、編集中のファイルはディスクの内容と違うからです。 保存していない変更に対しても補完や診断が効くのは、本文がこうして送られているためです。 以後の編集はtextDocument/didChangeで差分が送られ、versionが増えていきます。

05インデックスができるまで、サーバーは答えられない

ここで実際に踏んだ失敗を残しておきます。 最初の記録では、ファイルを開いた直後に定義ジャンプを聞いたところ、答えが空で返りました。

理由は、そのすぐ前に流れていた通知にありました。

サーバーは起動後にプロジェクト全体を読んでインデックスを作ります。 「どのクラスがどのファイルにあるか」の索引です。これが終わるまで、 クラス名から場所を引く質問には答えられません。10秒かかっています。

エディタを開いた直後だけ補完が効かない、という経験に心当たりがあれば、これがその正体です。 そして、この待ち時間は自動テストでも同じように効きます。 インデックス完了の通知を待たずに質問を投げるテストは、実装が正しくても落ちます。

06定義ジャンプの1往復を、まるごと見る

インデックスの完成を待ってから、あらためて聞きました。題材はこのファイルです。

5行目のGreeterにカーソルを置いて「定義へ移動」を要求します。

"line":4が5行目を指しているのは、LSPの行と桁は0から数えるためです。 人間が見る行番号より常に1つ小さくなります。ここは実装でよく間違えるところです。 characterも同じく0起点で、20はGreeterという語の内側にあたります。

返ってきたのはLocation（場所）という形です。中身は2つだけ。 uriがどのファイルか、rangeがその中のどこからどこまでか。 エディタはこれを受け取って、そのファイルを開き、その範囲を選択状態にします。 「定義へ移動」の実体は、この2つの数字の組を受け取ることだけです。

返るのは文字列ではなく、位置

ここが検索との決定的な違いです。grepが返すのは「その文字列が現れる行」で、 同名の別物や、コメントの中の同じ語も一緒に返ります。 言語サーバーが返すのはその名前が実際に指している定義そのものの位置で、ふつう1件です。 文字列が一致しただけの場所は、原理的に返りません。 ただし万能ではなく、返せなかったのか、そもそも無いのかはnullだけからは区別できません（§05）。

仕組みが分かれば、ほかの機能も同じです。メソッド名の上にカーソルを置いたとき（ホバー）:

中身はMarkdownです。エディタはこれを整形して吹き出しに出すだけで、 何を書くかはサーバーが決めています。rangeは「この範囲に対する説明ですよ」という印で、 エディタはその範囲に下線を引いたりします。

labelが一覧に表示される文字、insertTextが選んだときに挿入される文字です。 kindは種類を表す数値で、2はメソッド（5ならフィールド、7ならクラス）。 エディタが候補の横にアイコンを出せるのはこの数値のおかげです。 isIncomplete: trueは「まだ候補がある。文字が増えたらまた聞いて」という意味です。

08BEAR.Sundayの拡張は、この往復のどこに入るのか

ここまでのやりとりで、拡張が関わるのはサーバーが答えを作る一瞬だけです。 プロトコルの読み書きも、ヘッダーの組み立ても、phpactorが全部やります。

作るものは、このDefinitionLocatorというインターフェースを実装したクラス1個です。 「この位置にあるのが'app://self/user'という文字列なら、 src/Resource/App/User.phpの場所を返す」という判断だけを書きます。

そして、それをphpactorに見つけてもらうためにタグを付けて登録します。 タグの文字列はphpactorのソースで確認済みのものです。

やりたいこと付けるタグ
定義へ移動reference_finder.definition_locator
補完completion.completor
診断（波線）language_server.diagnostics_provider
コードアクション（電球）language_server.code_action_provider
型の解決worse_reflection.member_type_resolver

最後のworse_reflection.member_type_resolverだけ毛色が違います。 これは型推論そのものに口を出すための口で、 $client->get('app://self/user')の戻り値を具象クラスとして扱わせるのに使います。 文字列の中身を見て型を決める、という芸当がここで可能になります。

09AIがこれを読むと、何が変わるのか

最後に、いま作っているものがAIエージェントにとって何を意味するかを書きます。

AIがコードを調べるとき、いちばん素朴な手段は文字列検索です。 しかしapp://self/userという文字列をgrepしても、返るのは 「その文字が現れた行の一覧」でしかありません。 それが本当にリソースを指しているのか、対応するクラスが実在するのか、 コメントの中の書きかけなのか、検索結果からは分かりません。

言語サーバーが返すのは、この文書で見てきたとおり構造のついた事実です。

文字列検索が返すもの言語サーバーが返すもの
形行のテキストuri と range（機械が扱える座標）
件数一致した数だけ実際に指している定義、ふつう1件
誤り同名の別物・コメントも混ざる原理的に混ざらない設計（名前を解決してから答えるため）
未保存の編集反映されない反映される
存在しないとき「見つからない」としか言えないresult: nullが返る。ただし §05 のとおり、準備がまだのときも同じnull

最後の行には但し書きが要ります。 nullは「本当に無い」とも「まだ答えられない」とも読めるからです。 それでも、行のテキストが0件だったという事実より扱いやすいことは確かで、 インデックスの完了を待ってからのnullは「無い」と読んでよいという判断ができます。 条件つきであることを承知して使えば、AIが自分の調査結果を信じてよいかの材料になります。

MCPとの関係

同じ発想を別の道でやっているのが、PhpStormプラグイン側で進めているMCP （Model Context Protocol＝AIが外部ツールに事実を問い合わせる規約）です。 向いている先は同じ「AIに推測させず、事実を答える」ですが、 LSPはエディタが聞く規約、MCPはAIが聞く規約という違いがあります。 片方を作ればもう片方が要らなくなる、という関係ではありません。

10用語

LSP / Language Server Protocol
エディタと、言語の知識を持つ別プロセスとの間の共通の話し方。2016年にMicrosoftが公開。
JSON-RPC 2.0
「関数を呼んで結果をもらう」をJSONで表現する既存の規約。LSPはこれを土台にしている。
リクエストと通知
idがあるものがリクエスト（答えが返る）、無いものが通知（返らない）。
Location
場所を表す形。uri（どのファイル）とrange（どこからどこまで）の組。
range / position
位置。lineとcharacterで表し、どちらも0から数える。
capabilities
できることの申告。initializeの応答で返り、エディタのメニューの有効・無効を決める。
インデックス
「どのクラスがどのファイルにあるか」の索引。起動後に構築され、完成まで名前引きの質問には答えられない。
phpactor
PHPで書かれたPHP用の言語サーバー。単体で動き、拡張で機能を足せる。
DefinitionLocator
phpactorで「定義へ移動」に答える部品のインターフェース。BEAR.Sundayの拡張はこれを実装する。
WorseReflection
phpactorの型推論エンジン。「Reflectionより劣る」という自虐的な命名で、コードを実行せず静的に読むぶん精度が落ちることを指す。
MCP / Model Context Protocol
AIエージェントが外部ツールに事実を問い合わせるための規約。LSPと目的は近いが、聞く主体が違う。
